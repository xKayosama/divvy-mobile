The mobile client uses `EXPO_PUBLIC_API_URL` and relative paths such as `/auth/login`. The configured base URL must include `/api`, for example `http://<backend-host>:5000/api`. A physical phone needs a reachable backend hostname or computer LAN address; localhost refers to the phone itself.

## Authentication contract

- Deployment hardening (2026-10-19): registration validates string credentials, nonblank names up to 100 characters each, email syntax/length (254 maximum), and passwords of at least 8 characters and at most 72 UTF-8 bytes before hashing. Invalid input returns 400; duplicate registration races return 409. Emails are trimmed and lowercased. Login rejects malformed/oversized credentials with 400 but still accepts existing shorter passwords. Per-process, per-IP limits over 15 minutes are 20 unsuccessful login attempts and 5 registration requests; excess returns JSON 429 with Retry-After. A shared store or gateway limits and explicit trusted-proxy configuration are required when scaling or hosting behind a proxy.
- Startup validates MONGO_URI, JWT_SECRET (at least 32 UTF-8 bytes), PORT, and a positive JWT_EXPIRES_IN. `/api/health` remains process liveness; `/api/ready` checks MongoDB connectivity/ping and returns 503 during database failure or shutdown. SIGTERM/SIGINT drains HTTP and closes MongoDB within a 10-second deadline.

Source: `src/modules/auth/auth.routes.js`, `auth.controller.js`, `auth.middleware.js`.

- `POST /api/auth/register`: JSON `{ firstName, lastName, email, password }`. HTTP 201 returns `{ success: true, message, data: { user: { id, firstName, lastName, email } } }`. Registration does not return a token. Missing fields return 400; duplicate email returns 409.
- `POST /api/auth/login`: JSON `{ email, password }`. HTTP 200 returns `{ success: true, message, data: { token, user: { id, firstName, lastName, email, role } } }`. Invalid credentials return 401.
- `GET /api/auth/me`: bearer authentication; returns `{ success: true, data: { user: { id, firstName, lastName, email, role } } }`.
- `POST /api/auth/logout`: bearer authentication, no body. HTTP 200 returns `{ code: 200, success: true, message }` and revokes the submitted token. Clear local session on success or 401. On 500, allow a retry.
- Protected requests require `Authorization: Bearer <token>`.
- JWT expiration is configured by `JWT_EXPIRES_IN` (documented default: `7d`). No refresh endpoint is registered in the current auth router.
- Errors generally return `{ success: false, message }`.

## Password reset (implemented 2026-10-27)

Verified against `src/modules/auth/password-reset.controller.js`, `password-reset.email.js`, `auth.routes.js`, `auth.middleware.js`, and `src/modules/users/User.js` in the local backend.

- Public `POST /api/auth/forgot-password`: `{ email }`; trims/lowercases email, rejects malformed/oversized input with 400. Returns 200 `{ success: true, message }` with the same generic message for existing/unknown accounts and cooldown requests. No code or token is returned. Missing backend email configuration returns 503 globally. Known provider failures remove that issued code and retain the generic response; check backend logs for delivery failures.
- Public `POST /api/auth/reset-password`: `{ email, code, password }`; code is exactly eight digits including leading zeros. Password requires at least 8 characters and at most 72 UTF-8 bytes. Success 200 `{ success: true, message }`; invalid/expired/used codes return 400; service failures return 503. No automatic sign-in.
- Backend email delivery uses Resend HTTPS API. Set **backend-only** `RESEND_API_KEY` and `PASSWORD_RESET_FROM` with a verified sender/domain. Never put these in Expo public variables. No dependencies were added. Actual inbox delivery requires these settings and a reachable provider.
- Codes expire in 15 minutes, are stored as keyed HMACs in a query-hidden user field, and allow at most five attempts. Resend replaces the previous code, with a database-enforced 60-second account cooldown. Per-IP limits: five requests and twenty submissions per 15 minutes. Shared IP limiting is required when scaling, as with existing auth limits.
- A successful reset atomically writes the bcrypt password, consumes the code and increments `authVersion`. JWT creation carries that version; protected requests reject older versions. Missing versions count as zero for existing accounts/tokens. No data migration is needed. Existing sessions are rejected on their next request.
- Mobile: Login → Forgot password → email request → code/new password/confirmation → success → Sign in. Includes resend countdown, different-email action, inline validation, duplicate-submit guards, network/server feedback and no password/code in route parameters or persistence. Reloading the screen starts a fresh request flow.
- Regression tests cover both API contracts, form limits, generic responses, cooldown, delivery failure, expired/used codes, exhausted attempts, concurrent consumption and old-session invalidation. Tests mock MongoDB/email; live device and provider smoke tests remain necessary before release.

## Feature API map

### Dashboard spending periods (added 2026-10-16)

- Month-over-month comparison added 2026-10-16: nullable `data.spendingComparison` compares this_month with last month, or last_month with the preceding month; all_time returns null. Shape: `{ timeZone: "UTC", basis: "calendar_month", current: { startDate, endDate, amount, isInProgress }, previous: { startDate, endDate, amount }, difference, percentageChange, direction }`. Dates are inclusive labels. Difference is selected minus previous; direction is increase/decrease/unchanged. Amounts use cents and match selected spending totals. Percentage is signed, rounded to two decimals, and null whenever previous amount is zero, including both empty. Going from nonzero to zero returns -100. Only group expenses contribute; bills/settlements and current balances remain independent. Full calendar-month windows match existing period totals (including future-dated recorded expenses); `current.isInProgress` is true for this_month. Mobile shows the amount difference, prior calendar month name/total, percentage change when available, and an in-progress note inside the spending card. All time and older responses without comparison omit it. Zero prior spending is explained without showing a percentage. Comparisons use the selected period cache and refresh with existing dashboard invalidation.

- Category breakdown added 2026-10-16: `data.spendingByCategory` contains `{ category, amount, count, percentage }` entries for the selected group/period. Each expense contributes its full amount once; bills and settlements are excluded. Amounts accumulate in cents and reconcile with summary.totalExpenses/totalPaid. Entries sort by amount descending, then category alphabetically. Only recorded categories appear; no expenses returns `[]`. Percentages round independently to two decimals and may total 99.99 or 100.01. Legacy missing/unknown categories fall back to OTHERS; known casing/whitespace is normalized in the response. No schema changes, migration or new endpoint. Mobile displays a Spending by category card below the spending total, following the selected period. It shows category icons, currency amounts, counts, percentages and proportional bars. The first three categories appear initially with Show all/Show less; changing period/group resets expansion. Tapping a category opens Expenses with that category and the response period's inclusive date bounds. All time clears date bounds; each visit resets search, pagination and earlier filters. Parameters are validated before applying, and users can edit/clear the filters normally. Empty arrays show No spending in this period; older responses without the field omit the card.

- `GET /api/groups/:id/dashboard?period=this_month` accepts exactly `all_time`, `this_month`, or `last_month`; omission defaults to all_time. Invalid, blank, structured or repeated values return 400. Existing authentication/ACTIVE membership checks remain in place.
- Only `data.summary` (totalExpenses, totalPaid, totalOwed) and `data.recentExpenses` use the selected expense `date` range. Recent previews remain the newest five by date/createdAt. UTC calendar months include their full final day; this_month covers the entire month, including future-dated expenses within it. Balances/settlement effects use all history; bill totals, upcoming bills and reminders stay current.
- New `data.period` is `{ value, timeZone: "UTC", startDate, endDate }`; date labels are inclusive YYYY-MM-DD, or both null for all_time. Example this_month on 2026-10-16: startDate 2026-10-01, endDate 2026-10-31. No schema change or migration is required. Mobile provides This month, Last month and All time controls (default All time), with separate period/group query caches. Selection is scoped to its group; another group starts at All time. The spending card shows the period and inclusive UTC dates. Current balances and bill sections are explicitly distinguished from period spending. Pull-to-refresh/focus/resume/midnight refresh retain the selected period; bill/expense mutations invalidate every period for the group.

Routes use `/api/groups`, not `/api/households`. Responses use `data.group` / `data.groups`; related records use `groupId`.

- Group creation currency (verified 2026-10-22): `POST /api/groups` accepts `{ name, currency? }` with bearer authentication. Currency defaults to PHP when omitted, and string values are trimmed and uppercased. Supported creation currencies are the 155 current ISO 4217 currencies from SIX List One (published 2026-09-17), excluding funds, metals and test/no-currency codes. Mobile metadata in `src/features/groups/currencies.ts` matches backend `src/modules/groups/group.currencies.json`. Historical currencies such as BGN/HRK are excluded. Amounts use native ISO precision (0, 2 or 3 decimal places), with matching client/backend validation. Excess precision is rejected with 400 rather than rounded. The selector displays the selected precision. Blank, non-string and unsupported values return 400 before writes. HTTP 201 returns the saved currency in `data.group.currency`. Mobile offers a searchable currency selector with flags (regional globes where no single flag applies), PHP selected initially, and sends the selected code. Existing groups are unchanged; no exchange conversion is applied. Deploy the updated backend before using the new client: older controllers ignore currency on creation.

Group routes cover CRUD and membership, plus `/:id/expenses`, `/:id/bills`, `/:id/balances`, `/:id/settlements`, and `/:id/dashboard`. Standalone expense and bill routes also mount under `/api/expenses` and `/api/bills`. Inspect the relevant module routes/controllers for exact methods and payloads.

Receipt scan: `POST /api/groups/:id/receipts/scan`, bearer authentication and active group membership, multipart file field `receipt`. Supports JPEG, PNG, WebP, PDF up to 10 MB. Returns extracted receipt data requiring an editable review step; scanning does not create an expense. See the backend README for the full contract.

The backend also generates recurring bill occurrences. See its README and bills module before implementing recurring bill UI.

## Mobile receipt scanning (verified 2026-10-16)

Source: `src/modules/receipts/receipt.{routes,controller,schema,upload,ocr}.js` and backend README.

- `POST /api/groups/:id/receipts/scan` requires a bearer token and ACTIVE membership. Send multipart FormData with exactly one file under `receipt`, without other form fields. Do not set Content-Type manually; the runtime generates the multipart boundary. Maximum 10 MiB; JPEG, PNG, WebP and PDF supported by the backend, with content signatures validated.

Receipt fields: `isReceipt`, nullable merchant/date/currency/subtotal/tax/tip/total, items with nullable description/quantity/unitPrice/total, and warnings. Date is YYYY-MM-DD; currency is a three-letter code. No expense is created, no image attachment is persisted, and no public file URL is returned.

- Mobile supports taking a photo on native and selecting an image on native/web using SDK-compatible Expo ImagePicker. Images are normalized to JPEG with ImageManipulator, capped at 2400 pixels on the longest side, and checked against the upload limit. PDF selection is not currently exposed in mobile. The camera asks permission when used; the system image picker does not request broad photo-library access. Native camera/photo permission descriptions are configured through the plugin, with microphone permission disabled.
- SDK 57 installs `expo/fetch` as global fetch on native. Its multipart encoder does not support legacy React Native `{ uri, name, type }` objects. Native uploads append an `expo-file-system` File so the encoder can read its bytes; web uploads append a Blob. The upload helper checks file existence and size. Regression coverage runs the actual installed Expo multipart encoder against the new File-compatible object and verifies that the old descriptor is rejected.
- Scanning prefills an editable expense form with merchant description, total, date and item descriptions in notes. Missing totals/dates remain blank and require entry. Source photo, item details, subtotal/tax/tip, and warnings remain visible for comparison. Category, payer, participants and split are chosen by the user. Explicit review acknowledgement is required; a currency mismatch prompts entry of an amount in the group's currency, with no automatic exchange conversion. Saving uses the existing expense endpoint and cache invalidation.
- Both added modules are included in Expo Go. Existing custom development builds need rebuilding to include the packages and permission configuration. No native folders are edited manually.

## Settlements and repayments (verified 2026-10-16)

Source: backend commit `3469c76`, `src/modules/settlements/{Settlement.js,settlement.routes.js,settlement.controller.js,settlement.balances.js}`, balance and dashboard controllers.

- `GET /api/groups/:id/settlements`: ACTIVE membership and bearer authentication; returns `{ success: true, data: { settlements: [{ from, to, amount }] } }`. From/to are populated users. These are current suggestions, not payment history; recorded repayments reduce the suggested amounts.
- `POST /api/groups/:id/settlements`: body `{ to: userId, amount: number, paidAt: ISO timestamp, requestId?: string }`. Sender and recorder are always the authenticated user. Sending a different `from` is forbidden (403). Recipient must be a different ACTIVE member; amount must be positive, finite, safe in currency minor units, and match the group currency’s native precision. Payment date must be valid and not in the future. Invalid input returns 400. Success returns HTTP 201 with `data.settlement`; from/to/recordedBy are raw IDs in this response.
- `GET /api/groups/:id/settlements/history?page=1&limit=10`: returns `data.settlements` populated at from/to/recordedBy plus `pagination: { page, limit, total, totalPages }`. Page must be a positive integer (maximum 1,000,000); limit 1–100. Order is paidAt, createdAt, _id descending. Mobile handles missing populated accounts.
- Balances/dashboard retain purchase `paid`/`owed` totals and add `settlementPaid`, `settlementReceived`; net is `paid - owed + settlementPaid - settlementReceived`. Bills do not participate directly; newly paid bills contribute through their linked expense. Suggestions/balances use ACTIVE group membership.
- Mobile provides a dashboard Settle up action, suggestions (prefill only the current sender's payments), paginated history, recipient/amount/date entry, explicit review, and success confirmation. Only payments sent by the current user can be recorded. Date selection is converted from local calendar midnight to ISO; today/past dates are allowed. Saving invalidates history and Dashboard tags, refreshing balances and suggestions. Expense/member mutations also refresh suggestions through the Dashboard tag.
- Duplicate protection added on 2026-10-16: payments must match an outstanding suggested sender/recipient pair and cannot exceed its remaining amount. Settled/stale/excessive requests return 409. Suggestions are deterministically ordered by user ID. A unique per-pair balance-state claim prevents two concurrent requests from recording against the same snapshot; partial payments can be followed by the remaining amount after refresh.
- Mobile creates a requestId when reviewing a payment and reuses it on retry. IDs are scoped to group/sender, must be 8–128 alphanumeric/underscore/hyphen characters, and are protected by a unique partial index. Identical retries return HTTP 200 with the original payment; changed details under the same ID return 409. The backend ensures unique indexes before writes and fails closed if they cannot be created.
- The form offers only outstanding recipients, shows the remainder, guards duplicate taps, and fetches current suggestions immediately before saving. 409 refreshes history/suggestions/dashboard. No repayment edit/delete endpoint is present. Recording a payment does not transfer money.

## Native currency precision (verified 2026-10-22)

- Source: backend `src/utils/{money.js,currency-precision.json}` and mobile `src/features/groups/{money.ts,currencies.ts}`. Existing stored amounts remain numbers in major units; no exchange conversion, migration or backfill is performed.
- Expense and bill create/update and settlement recording validate positive amounts with the group currency’s native precision and safe integer minor-unit bounds. Examples: JPY 1, PHP 0.01, KWD 0.001. Exact participant shares allow zero with the same currency precision; percentages retain two decimals and must total 100%. Equal splits conserve minor units, giving the remainder to the first participant. Percentage splits reconcile the last share and redistribute excess rounding from earlier shares if needed to prevent negative shares.
- Dashboard summaries, category totals, comparisons, bill reminders, member balances and settlement suggestions/payments use integer currency minor units. Recurring bills preserve and validate the source amount. Monetary displays, amount placeholders, input validation, split previews and receipt prefills use the group/receipt currency precision. Receipt prefills preserve excess decimals for correction rather than silently rounding. OCR recognizes explicit current ISO codes and native decimal totals.
- Legacy values incompatible with native precision are never rewritten. Balance/dashboard/settlement calculations return 409 with a review message instead of silently rounding; incompatible recurring sources are skipped and logged. Detail displays preserve historical fractions for review. Review any such records against original receipts before correction.
- `PUT /api/groups/:id` validates currency codes and returns 409 for changing currency once expenses, bills or settlements exist, preventing reinterpretation of recorded money. Mobile settings allow owners to change currency only while the group has no recorded expenses, bills or settlements. Deploy the backend and mobile together; older clients assume two decimals.

## Itemized expenses (verified 2026-10-22)

- Standard expenses remain the default with EQUAL, EXACT and PERCENTAGE splits. `POST /api/groups/:id/expenses` additionally accepts `splitType: "ITEMIZED"` and `items: [{ description, quantity?, amount, memberIds: [userId] }]`, alongside the existing description, total amount, category, paidBy, date and notes. Do not supply `participants` for ITEMIZED: the server derives the unique participant list and amounts from items. Existing authentication and ACTIVE group membership rules apply to payer and every assigned member.
- Each item’s amount is its full line total for all quantity, not a unit price. Quantity defaults to 1 when omitted, must be positive, at most 1,000,000 and have at most 3 decimals. Item amounts are nonnegative and use the group currency’s native precision; the positive expense total must exactly match the sum of line totals. Require 1–100 items, nonblank descriptions up to 200 characters and at least one unique valid member ID per item. Invalid input returns 400 before any write. Unsupported/inactive item assignees are rejected by the existing membership checks. Client-submitted participant totals are never trusted.
- Each line splits equally among its assigned members in integer native currency minor units. The first assigned member receives that line’s rounding remainder. Shares aggregate across items, including zero-cost items, and reconcile exactly to the expense amount. Existing dashboard, category, balance and settlement calculations consume those derived participant shares, counting each expense once.
- The Expense schema adds ITEMIZED to splitType and an optional items array, storing assigned member IDs as User references. Standard/legacy expenses retain the default EQUAL behavior and omit items; no migration or backfill is required. Expense list/detail/create/update responses preserve itemized metadata; detail screens show quantity, line total and assigned members with unavailable-account fallbacks.
- `PUT /api/expenses/:expenseId` retains itemized mode/items when omitted and revalidates/recalculates shares. An explicit conversion to a standard split clears saved items; standard split requests must not include nonempty items. Mobile loads itemized expenses back into the item editor and warns before saving a conversion to Standard.
- Mobile offers Standard / Itemized, defaults new manual and receipt expenses to Standard, and preserves both drafts while switching. Item cards can collapse, support add/remove/edit, and open a member-assignment sheet with Select everyone, clear, and unavailable-member removal. The preview displays item/expense totals and per-member shares; invalid or unreconciled itemization cannot save. One payer is retained. Tax and tip can be added as separate positive/zero assigned lines. Negative discount lines and proportional adjustment allocation are not supported in this version.
- Receipt scan items prefill item descriptions, quantities and extracted line totals when Itemized is selected. Missing values remain blank for review; unit prices are never mistaken for line totals, and no members are assigned automatically. Tax/tip differences must be resolved explicitly using assigned lines or corrected totals. Existing original-receipt comparison, warnings, currency mismatch messaging and review acknowledgement remain required. No expense is created by scanning.
- Deploy the backend before the mobile itemized flow. Older backend versions do not accept ITEMIZED; older clients may not support viewing/editing this split type.


## Itemized tax and tip allocation (verified 2026-10-22)

- ITEMIZED create/update requests accept optional `adjustments: { tax?: { amount, allocation }, tip?: { amount, allocation } }`. Each amount is a nonnegative number with native currency precision; allocation is `EQUAL` or `PROPORTIONAL`. Missing adjustments preserve legacy behavior. The expense total must equal line totals plus tax plus tip. Standard requests reject adjustments; converting to Standard clears stored adjustments.
- Tax and tip independently allocate among the unique members assigned to items, in first-appearance order. EQUAL includes members assigned only zero-cost items. PROPORTIONAL uses each member’s allocated item subtotal before either adjustment (including existing per-line rounding), so tip never includes tax. A positive proportional charge with zero item subtotal is rejected; choose EQUAL instead. Zero charges are allowed in either mode.
- All calculations use exact integer native minor units. Each adjustment uses largest-remainder allocation, with ties resolved by member first-appearance order. Server-derived participants include items and both charges, so balances and settlement suggestions include extras once. Submitted participant totals remain forbidden for ITEMIZED.
- Responses persist adjustment amounts and methods. Partial updates retain omitted adjustments and revalidate/recalculate; supplying `adjustments` replaces the entire adjustment object, so `{}` clears both. Omit a tax/tip key to remove it when replacing the object. No data migration is required.
- Mobile provides tax/tip amount fields and independent Equally / By item amounts controls, defaulting to proportional. Blank means zero. Receipt tax and tip prefill for review; remove duplicate tax/tip item lines before using dedicated extras. Existing receipt review and total checks remain. Draft changes participate in unsaved-change protection. Preview shows each member’s item subtotal, tax, tip and final total; details show saved charges and methods, and editing restores them.
- Deploy the backend before the updated itemized mobile flow. Older clients do not understand saved adjustments and should be updated before editing these expenses.


## Split by shares (verified 2026-10-22)

- Standard expenses additionally support `splitType: "SHARES"` with `participants: [{ userId, shares }]`. Shares must be numeric positive whole numbers from 1 to 1,000,000. A 2:1 weight divides the total in that ratio. Existing authentication, unique participant, ACTIVE membership and payer checks apply.
- The server calculates participant amounts from weights, ignoring any submitted participant amounts. Calculations use integer native currency minor units and exact integer arithmetic. Fractional allocations are floored, then remaining units go to the largest fractional remainders, with participant order breaking ties. Amounts always reconcile to the expense total, including JPY and KWD.
- Responses persist `participants[].shares` alongside calculated amounts. Updates retain omitted weights and recalculate when the total changes. Mobile loads weights when editing and displays them in expense details. Switching split modes replaces the corresponding participant metadata. No migration is required; existing splits retain their behavior.
- Mobile keeps Standard and Equal as the defaults. By shares includes an icon, defaults each selected member to 1, supports number entry and plus/minus controls, and previews each amount and total shares before saving. Invalid weights block saving.
- Deploy the backend before using SHARES on mobile. Older backend versions do not support this split type.

## Recurring expenses (verified 2026-10-22)

- `POST /api/groups/:id/expenses` accepts optional `recurring: { frequency: "WEEKLY" | "MONTHLY" | "YEARLY", endDate?: "YYYY-MM-DD" | null }`. The first expense is recorded normally and owns the schedule. Omission preserves one-off behavior. The backend validates the schedule before writing. Dates use UTC; end dates include the entire final UTC day and cannot precede the first expense date. Monthly/yearly dates derive from the original anchor, preserving month-end/leap-year behavior without drift.
- Expense responses optionally include `recurring: { frequency, anchor, endDate, paused, nextNumber, nextDate, lastError }`. Generated occurrences instead include `recurrenceSourceId` and `occurrenceNumber` and have no schedule. They reuse the source's description, amount, category, notes, payer and full participant split, including SHARES weights, ITEMIZED lines/assignments, tax and tip. Each recorded entry contributes to balances and spending once.
- `PATCH /api/expenses/:expenseId/recurrence` accepts `paused?: boolean` and/or `endDate?: "YYYY-MM-DD" | null`. Existing bearer/ACTIVE membership checks apply. Only originals with a schedule accept management; invalid input returns 400, nonmembers 403, and concurrent processing/progress changes 409 with retry guidance. A successful response contains the updated populated `data.expense`.
- Pause prevents future generation. Resume skips missed paused dates and continues at the next future anchored occurrence. Extending a completed schedule also restarts from the next future date. Clearing the end date removes the limit. Next date null means no remaining occurrences within the limit; pause is independent. Future source edits reuse the new amount/payer/split; existing generated records are not rewritten. Original expense dates/frequency remain fixed to preserve the anchor; manage pause/end dates in details. Generated occurrences edit independently. Deleting the original stops the schedule and preserves existing occurrences.
- The backend starts a recurring-expense worker after connecting, installs the unique partial `(recurrenceSourceId, occurrenceNumber)` index before starting, and runs every 60 seconds with a local overlap guard. Each due occurrence uses a source lease plus an atomic upsert with a permanent unique occurrence key. Progress advances only after persistence. Retries and overlapping servers cannot insert duplicate occurrence keys; duplicate-key errors are accepted only after verifying the exact occurrence exists. Expired leases recover after 60 seconds. Source edits, deletes and schedule controls reject active leases. Deletion of a generated entry still awaiting its source checkpoint returns 409, preventing recreation after an interrupted write/checkpoint. The worker catches up after downtime in bounded batches of 120 per source; paused periods are skipped on explicit resume.
- The worker rechecks the group and ACTIVE membership of payer and all participants before generating. Unavailable members/groups automatically pause the schedule with a review message; no invalid expense is written. Native currency precision and participant totals are validated. Worker failures retain progress for retry and are logged. An already processing occurrence may finish before a pause request can succeed.
- Mobile provides an optional Repeat this expense control on creation, weekly/monthly/yearly choices, inclusive optional end date, list schedule badges, and details controls for pause/resume/end-date changes. Source editing explains the future-entry scope and fixes the anchor date. Generated details link to the original schedule. Create drafts include schedule fields in unsaved-change protection. Successful schedule mutations invalidate expense list/detail and dashboard caches.
- Deploy the backend before this mobile flow. No data migration is required for existing one-off expenses; the new indexes are installed on startup. Run the backend continuously for scheduled generation; stopped servers catch up when restarted. This records expenses automatically and does not initiate payment transfers.


## Paid bills and linked expenses (verified 2026-10-23)

- Before this change, PAID bills only affected bill status totals/reminders. Balances, settlement suggestions and expense spending read Expense records only. That remains the ledger rule: a newly paid bill now contributes once via its linked expense; the bill itself is never added to spending or member balances. Bill paid totals remain separate status summaries.
- `POST /api/bills/:billId/pay` accepts `{ paidBy, splitType, participants }`. Standard split types EQUAL, EXACT, PERCENTAGE and SHARES use the same server calculators/native precision as expenses. EQUAL participants need userId; EXACT adds amount, PERCENTAGE adds percentage, and SHARES adds whole-number shares. Explicit unique participants and an ACTIVE payer/member set are required. Bills do not support itemized payment entry in this flow. Confirming does not transfer money.
- The expense copies the bill name/amount/notes, maps its category, and uses the server-owned payment time as its expense date. RENT/INTERNET/EDUCATION retain their expense category; ELECTRICITY/WATER/GAS/PHONE map to UTILITIES, SUBSCRIPTION to SUBSCRIPTIONS, ASSOCIATION_DUES/MAINTENANCE to HOME_MAINTENANCE, and remaining categories to OTHERS. Save bill edits separately before confirming payment. Direct PAID creation is rejected. Legacy PUT PAID transitions also require explicit split settings and delegate to the same payment logic.
- Bill responses expose nullable `expenseId` and `paymentPending`; Expense responses expose nullable `billId`. Payment success returns `{ data: { bill, expense: { _id, billId } } }`. Ordinary expense GET provides full populated details. Both details screens link to the other record. Paid bills and their linked expenses cannot be edited/deleted independently, so payer/amount/split cannot drift. Recurring bills continue to create unpaid occurrences; each occurrence requires its own payment confirmation and gets its own expense.
- Payment first atomically reserves its expense ID and immutable payer/split/time snapshot on the unpaid bill, comparing its last update time and requiring expenseId null. Concurrent bill edit/delete operations also require no reservation. Expense insertion uses atomic upsert plus a unique partial billId index; finalization marks PAID only after that expense persists. Identical retries reuse the same expense/time; conflicting payer/split retries return 409. Interrupted writes return a recoverable error rather than creating another expense. `POST /pay` with `{ resume: true }` finishes only an existing frozen reservation without changing its settings.
- A recovery worker runs on startup and every 60 seconds, installing the unique expense link index before serving requests. It completes reservations after crashes between insert/checkpoint; overlapping workers are safe. Pending reservations are locked against bill edits/deletion and display Finish saved payment in mobile. Internal snapshots are excluded from serialized bill responses. Group access is checked on every user request before exposing payment state.
- Existing PAID bills are not automatically backfilled: users may already have manually recorded those expenses. Their details explain that they have no linked expense. No balance changes are made to legacy history. Deploy the backend before the updated payment UI; older clients sending payer-only paid requests receive 400 until updated. Backend startup installs the new index; no backfill/migration is run.
- Mobile offers payer and participant sheets, Equal / By amount / By percent / By shares, and a native-currency allocation preview before confirmation. Successful payment opens bill details and refreshes bill/expense/dashboard caches, including spending periods and balances. Recoverable 409/503 responses also refresh state so a frozen payment can be resumed safely.

## Group soft deletion and restoration (verified 2026-10-23)

- Existing `DELETE /api/groups/:id` remains permanent hard deletion, including memberships, expenses, bills and settlements. It remains owner-only and also works on soft-deleted groups. Soft delete is a separate `POST /api/groups/:id/soft-delete`; restore is `POST /api/groups/:id/restore`. Both require the authenticated active owner. No child records or memberships are deleted by these new actions.
- Group stores nullable `deletedAt` and `deletedBy`. Normal model reads, counts and updates filter deletedAt null (including legacy records without the field). Only trusted lifecycle code opts into deleted records; the opt-in flag is removed before MongoDB execution. Normal group lists also exclude deleted populated references. Group-scoped APIs return 404 for soft-deleted groups; standalone expense/bill read/write/payment/schedule routes also check their parent group, preventing access through child IDs.
- `GET /api/groups/deleted` lists only groups owned by the current user, with id, name, currency, icon, role and deletedAt. Owners can restore retained data and memberships. Permanent deletion is still irreversible; previously hard-deleted records cannot be restored. No backfill or automatic purge is performed.
- Recurring bill/expense workers and pending bill-payment recovery skip deleted groups. Soft deletion pauses recurring expenses; restoration ensures they remain paused so the owner must explicitly resume using the existing skip-missed-dates behavior. Restoration advances recurring-bill source cursors past missed periods, retaining existing bills and producing only future occurrences. Pending payments saved before deletion remain preserved and recover only once the group is active again. Operations already in flight can finish into retained history, which stays inaccessible while the group is deleted.
- Mobile owner settings have a named soft-delete confirmation explaining retained data and discarded unsaved settings. Groups has a Deleted groups screen with restore actions and scheduling guidance. Lifecycle mutations refresh group, expense, bill, settlement and dashboard caches. The permanent-delete endpoint is retained; this change does not add a permanent-delete mobile button.
- Deploy the backend before the mobile actions. Existing active groups require no migration. Restored groups keep their financial history and currency eligibility rules.

## Group activity history (verified 2026-10-24)

- `GET /api/groups/:id/activity?page=1&limit=20` requires bearer authentication and ACTIVE group membership. Deleted groups are inaccessible until restored. Positive page up to 1,000,000 and limit 1–100; malformed/repeated parameters return 400. Returns `{ success: true, data: { activities, pagination: { page, limit, total, totalPages } } }`, newest `occurredAt`, then `_id` first.
- Entries contain `_id`, `actor` (populated firstName/lastName/_id or null), `action`, `targetId`, `label`, `occurredAt`, optional `changes` and `snapshot`. Actions: EXPENSE_ADDED, EXPENSE_EDITED, EXPENSE_DELETED, BILL_PAID, GROUP_UPDATED. Changes map field names to `{ before, after }`. Expense snapshots preserve amount, currency, description, date, payer ID, calculated splits/weights, item assignments, adjustments and notes; no email/token fields. Settings record changed name/icon/currency only. No-op settings/expense edits and rejected operations produce no entries. Schedule pause/resume/end-date changes use EXPENSE_EDITED. Automatically generated recurring expenses use null actor and `snapshot.automatic: true` (System).
- Recorder identity comes from the authenticated user, independently of the payer. Bill reservations freeze recordedBy/currency with payment settings, so recovery and retries retain the original recorder. Deterministic event document IDs deduplicate bill payments and expense additions/deletions independently of optional indexes. Paying a bill emits BILL_PAID only, rather than an additional expense-created event for the same action. Legacy reservations without a recorder use an unavailable-account fallback.
- Activity is a separate collection; expense deletion preserves its historical snapshot. Soft-deleted groups retain history; permanent group deletion removes it. There is no client write/edit/delete activity endpoint. Existing financial history is not backfilled because past recorder/edit identities cannot be inferred reliably. History does not affect balances or currency-change eligibility.
- Activity writes follow successful domain writes. Logging failures are reported in server logs and do not turn completed financial writes into retryable errors. This is an informational history, not a transactional audit ledger: a database failure between the domain write and event insert can leave a missing entry. Recurring/payment retries deduplicate events when their original work is retried. Monitor `Activity history write failed` on the server.
- Mobile Group → Activity history offers pagination, refresh, icons, names/timestamps and expandable before/after details with native currency precision. Successful expense/bill/settings mutations invalidate history caches; opening the screen refetches. No new mobile dependency is needed. Deploy the backend before opening this screen; existing records need no migration.
